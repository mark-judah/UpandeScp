# Upande-Scout QR Scanner: Match the Simplified Two-Line Payload

**Date:** 2026-05-28
**Status:** Approved for implementation
**Repo touched:** `~/stive/code/reactnative/Upande-Scout/upande_scout_rn` (this spec lives in `upande_scp` because that's where the QR payload is generated and where our spec convention lives)

## Problem

The Frappe backend QR payload was simplified in `upande_scp/serverscripts/qr_generator.py::build_chemical_qr_payload` to two lines:

```
<chemical_name>
<qty> <uom>
```

The React Native scanner in `app/(tabs)/chemical/plan-details.tsx::handleConfirmChemicalScan` (lines ~563–660) still parses the legacy `KEY: VALUE` format and validates **WO, CHEM, QTY, UOM, GH, SE, DATE**. Every scan against a new label fails with cascading "Missing WO / Missing CHEM in QR" errors, so operators stop scanning.

## Fix

Replace `parseQr` with a two-line parser, and trim validation to chemical-name + quantity only. UOM, WO, SE, GH, DATE checks are dropped — none are present in the new payload, and the upstream context (the plan the operator opened) already enforces WO/SE/GH identity.

## Parser

Operate on the raw scan text:

1. Split on `\r?\n`, trim each line, drop empties.
2. **Line 1 →** `chem` (chemical name, as printed).
3. **Line 2 →** match against `^([0-9]+(?:\.[0-9]+)?)\s*(.*)$`:
   - capture group 1 → `qtyValue` (parsed as `Number`)
   - capture group 2 → `qtyUom` (trailing unit string, trimmed; may be empty)

If line 2 is missing or doesn't match the numeric pattern, report **"QR is not a chemical label"** and abort. No fallbacks to the legacy keyed format.

## Validation

In order, stopping at the first failure:

1. **Chemical name** — reuse existing `normalizeText` (lowercase, collapse whitespace, strip non-`\w\s-./`) and the existing substring-either-direction fuzzy match against `scanTarget.itemName || scanTarget.itemCode`.
   - Mismatch → `CHEM mismatch (scanned <name>)`
2. **Quantity** — `Math.abs(parsed.qtyValue − Number(required.requiredQty)) <= 0.01` where `required` is the `scanItems` entry for the target item.
   - Missing numeric value → `Missing QTY in QR`
   - Out of tolerance → `QTY mismatch (scanned <value>)`

UOM is **captured but not validated**. Reason: the user explicitly scoped validation to name + quantity, and `kg`/`L` mix-ups would surface as a quantity mismatch anyway (different magnitudes).

## Stored scan detail

`chemical_scan_details[itemCode]` shape collapses to:

```ts
{
  chem: string,
  qtyValue: number | null,
  qtyUom: string,
  qtyRaw: string,
  raw: string,
  validatedAt: string,
}
```

`wo`, `se`, `gh`, `date` are removed. Before deleting, grep the RN repo for reads of those keys on `chemical_scan_details` entries — the only writer is `handleConfirmChemicalScan`, but a reader elsewhere would need to be updated or kept.

## Out of scope

- Camera UI, beep sound, auto-confirm `useEffect`, and `chemical_scans` persistence stay unchanged.
- `qr_generator.py` already emits this format — no Python changes.
- The label print pipeline (`spray_plan_labels.py`) is untouched.

## Files touched

- `app/(tabs)/chemical/plan-details.tsx` — replace `parseQr` (~40 lines) and validation block (~55 lines) inside `handleConfirmChemicalScan`. Expected net diff: ~−70 lines.

## Verification

Manual scan flow on a dev build:
1. Open a spray application plan with at least one chemical row.
2. Scan a label generated by current `build_chemical_qr_payload`.
3. Expected: row marks as scanned, no "Missing WO/CHEM" alert.
4. Scan a label for the *wrong* chemical → `CHEM mismatch` alert.
5. Manually edit a QR (e.g. via a test generator) to print the wrong qty → `QTY mismatch` alert.
6. Confirm `chemical_scan_details[itemCode]` in the cached plan contains `chem`, `qtyValue`, `qtyUom`, `qtyRaw`, `raw`, `validatedAt` — and none of `wo/se/gh/date`.
